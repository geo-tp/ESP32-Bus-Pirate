Bench pre-flight checklist

Separate tool, terminal, wiring and target issues before starting a protocol recipe. This checklist gives you a safe known-good baseline, then one passive first probe.

Step 1

Check the tool before wiring the target

Start with only the ESP32 Bit Pirate connected over USB. This confirms the terminal, firmware build and menu system before a target circuit can confuse the result.

Ready state

The CLI responds, the system shell shows board and memory information, the manual opens, and the mode selector is reachable. That gives you a clean baseline before wiring anything else.

Step 2

Build the wiring plan before touching pins

Treat this as a short pre-flight note, not a full project log. The goal is to avoid guessing once the target is powered.

  1. Identify the target voltage and where ground is available.
  2. Choose exposed board GPIOs, not just ESP32 chip pins copied from another variant.
  3. Mark signal direction: RX/TX, SDA/SCL, MOSI/MISO/CS/CLK, DQ, CAN TX/RX or module IRQ pins.
  4. Decide the first passive command you will run before any write, erase, jam, replay or transmit action.

Safety rule

Connect ground first and keep outputs idle until voltage, pin direction and bus ownership are clear. Pull-ups help compatible buses, but they do not make an unsafe voltage safe.

Step 3

Pick one passive first probe

After the wiring plan is clear, run a read-only or observation command that matches the target. The first probe should answer one question: is the bus alive and wired the way you think?

  • I2C sensor or EEPROM: enter mode i2c, then run scan before any register write.
  • SPI flash or EEPROM: enter mode spi, then try a JEDEC-style read such as [0x9F r:3] or open the EEPROM shell and start with Probe.
  • Unknown GPIO line: use wizard <pin>, sniff <pin> or measure <pin> before driving the line.
  • UART or AT modem: start with read, autobaud, ping or the AT shell before sending destructive configuration commands.

Result

What success looks like

You know the ESP32 Bit Pirate is responsive, which firmware and board state you are using, which pins and voltage you intend to touch, and which first passive command proves the target is reachable.

Troubleshooting

  • If the tool check fails with no target connected, fix USB, terminal speed or firmware before adding hardware.
  • If the target voltage or pin direction is unknown, stop at the wiring plan and use a datasheet, board page or multimeter first.
  • If the passive probe changes on every run, treat the wiring or pull-up state as unresolved before moving to write actions.

Next steps

  • Use the logic-level and pinout recipes before connecting an unfamiliar board.
  • Save a known-good pin set with the profile shell once a setup is stable.
  • Move to the protocol-specific recipe only after the passive probe is repeatable.

bench pre-flight checklist FAQ

Is this a replacement for a protocol recipe?

No. It is a short baseline before the real workflow. Use it to confirm the terminal, firmware state, wiring plan and first safe probe, then continue with the I2C, SPI, UART, DIO or module-specific recipe.

Should I run it every day or only on new targets?

Run the full checklist on new hardware, after flashing new firmware, after changing boards, or before a risky bench session. For a known stable setup, the tool check and passive first probe are usually enough.

What makes a good first probe?

A good first probe observes or identifies without changing target state: an I2C scan, a SPI JEDEC read, a GPIO wizard/sniff/measure command, a UART read/autobaud check, or a module status command.
